Admin Panel — Architecture & Roadmap

Plan for a login-gated admin console that lets the mission's team upload gallery photos (and eventually manage more site content) without touching code. Lives in its own repo and its own Cloudflare Worker, completely separate from the public site. Checkboxes persist in this browser via localStorage. Update this file in place as decisions get made and phases ship — don't create a second doc for the same project.

⛔ STRICT RESTRICTION — Do not touch the existing kriyayogamission dev/production project

This admin panel is a net-new, fully separate initiative. Under no circumstances should building, testing, or deploying it involve modifying the existing public site's live repo, Cloudflare projects, or configuration. Specifically, anyone (human or agent) working on this admin panel must never:

  • Push commits, open branches, or edit files directly in the kriyayogamission repo (public site) for admin-panel work. The admin panel lives entirely in its own kriyayogamission-admin repo.
  • Change Cloudflare settings, env vars, secrets, custom domains, DNS records, or build configuration on the existing kriyayogamission (production) or kriyayogamission-dev (dev) Worker/Pages projects.
  • Trigger a production deploy, deploy hook, or rollback on the existing site as a side effect of admin-panel work, without explicit, separate confirmation.
  • Delete, overwrite, or restructure any file in the public site (e.g. Gallery.astro, src/data/site.ts, worker.js) outside of the one explicitly-reviewed, explicitly-approved cross-repo change described later in this doc (wiring D1 fetch into Gallery.astro) — and even that change must be proposed, reviewed, and tested on dev first, never applied straight to main/production.
  • Reuse, repurpose, or quietly reconfigure the existing R2/D1/Access resources that back the public site — any new resource this project needs (buckets, databases, Access applications) must be newly provisioned for the admin panel, not retrofitted from production ones.

If any step in this roadmap seems to require touching the existing dev or production project/config, stop and get explicit human sign-off before proceeding — do not assume it's fine because it's "just a small change."

Why a separate repo and a separate Worker?

The public site (kriyayogamission/kriyayogamission) is a fully static Astro build (output: "static") — no server-side rendering, no database, every page baked into plain HTML at build time. That's deliberate: it's fast, cheap, and great for SEO. An admin console is the opposite kind of application — it needs auth, file uploads, and a database — so bolting it onto the same static site would mean dragging the whole public site into a heavier rendering model it doesn't need. Keeping the admin panel as its own repo (kriyayogamission-admin) deployed to its own Cloudflare Worker project means: independent deploys (an admin panel bug can't break the public site), independent scaling/cost tracking, and a clean mental model — "the public site" and "the internal tool that manages some of its content" are different programs that happen to share some Cloudflare account-level resources (R2, D1).

Tech stack decision: "what if we use Python and React?" DECIDED

Split answer — React: yes. Python: no. Here's the reasoning for each half:

React is a good fit for the frontend. The public site is static specifically because it needs to be fast and indexable by Google — neither of those pressures apply to an internal admin tool that only a couple of trusted people will ever open. A React single-page app (built as static files via Vite) is a perfectly reasonable, even good, choice here: forms, live image previews, drag-to-reorder, inline editing — all things React handles well. The built React app still just ships as static JS/CSS/HTML files, served from the admin Worker's static assets binding, exactly like the main site's Worker already serves its own static build today.

Python is not recommended for the Worker/backend logic. Cloudflare does offer "Python Workers," but it's explicitly a beta product that runs Python via Pyodide (a full CPython interpreter compiled to WebAssembly) — meaning slower cold starts, a much larger deployed bundle, and only a curated subset of PyPI packages actually work (pure-Python only; most packages with C extensions don't run at all in the WASM sandbox). R2, D1, and Cloudflare Access integration are all first-class, mature, and fully documented in JavaScript/TypeScript — Python support lags behind and has rougher edges for exactly the bindings this project needs most. There is no part of this admin panel's backend (checking an Access header, writing a file to R2, inserting a database row) that benefits from Python specifically — introducing it would just mean maintaining two languages across one small project for no technical gain. The existing worker.js already proved this pattern works well for the /api/contact route; the admin Worker's API routes should follow the same approach.

Cloudflare language support — full comparison

Cloudflare Workers run on V8 isolates (the same engine inside Chrome), not containers or VMs — that's the single biggest factor behind every efficiency difference below. Anything that runs as native JS on V8 is fast by default; anything else has to either compile down to JS or run inside a WebAssembly sandbox, with real trade-offs.

LanguageHow it runsCold startStatus
JavaScriptNative on V8 isolatesFastest (sub-5ms typical)GA, reference implementation
TypeScriptTranspiled to plain JS at deploy time (esbuild) -- zero runtime costIdentical to JSGA, our default
"Node.js" (nodejs_compat flag)Not a separate runtime -- polyfills some Node built-ins on top of the same JS/V8 engineSame as JS/TSGA compatibility layer, not a language
PythonPyodide -- full CPython compiled to WASMNoticeably slowerBeta -- not recommended for latency-sensitive production work
RustCompiled ahead-of-time to WASM (workers-rs)FastGA -- best for CPU-heavy work, not needed here
Go / C# / C++WASM via Emscripten/Go-WASM/BlazorSlow, large bundlesCommunity-only, not recommended

TypeScript vs. Node.js -- clarifying the real choice

These aren't actually competing options. TypeScript is a programming language (compiles to plain JS before anything runs). Node.js is a JavaScript runtime -- a way of executing JS on a server you manage, completely separate from Cloudflare Workers' own V8-isolate runtime. The real decision is Cloudflare Workers vs. a traditional Node.js server, not TS vs. Node.

A traditional Node.js server genuinely wins when you need: full filesystem access, native npm packages with compiled C/C++ bindings, no per-request CPU time ceiling, or a long-running process (a persistent WebSocket server, a continuous background job queue). None of that applies to this admin panel -- checking an Access header, writing a file to R2, and querying D1 are all officially and natively supported inside a Cloudflare Worker today.

Choosing a separate Node.js host instead would mean: a second hosting platform outside Cloudflare, losing in-process R2/D1 bindings (would need slower HTTP calls instead), taking on server management (patching, scaling, uptime) ourselves, and paying for always-on hosting instead of Workers' generous free tier. Verdict: TypeScript on Cloudflare Workers, not a separate Node.js server.

React on Cloudflare -- deployment patterns, and why the public site stays Astro

Cloudflare supports React well in three different shapes: a static SPA (Vite + React, ships as plain static files, blank page until the JS bundle runs -- fine for an internal tool, bad for SEO), server-rendered React (Next.js/Remix via Cloudflare's official adapters, real HTML on first paint but every request now does live rendering work in a Worker), or React as islands inside Astro (@astrojs/react -- only the specific component that needs interactivity ships React/JS, everything else on the page stays static HTML).

Admin panel: static React SPA is the right fit -- no SEO requirement, tiny trusted audience, the blank-until-JS trade-off doesn't matter. Public site: stays Astro, deliberately not migrated to React or Next.js -- the public site already has strong, hard-won Lighthouse/PageSpeed scores (see docs/vulnerabilities-and-roadmap.html) built on Astro's zero-JS-by-default model, and switching frameworks would risk regressing that for no real benefit. If a future public-site feature ever needs genuinely heavy client-side interactivity, add it as a React island on just that one component -- not a wholesale framework swap.

Access management (IAM) for the login page

Cloudflare Access sits in front of the admin Worker at Cloudflare's edge, before any request reaches our code. An Access Application gets scoped to the admin domain/path (e.g. admin.kriyayogamission.org/*), with a policy allowlisting specific email addresses. Visitors hitting that path get a Cloudflare-hosted login screen, and only allowlisted emails get through. No password storage, no session management, no "forgot password" flow to build -- all of that is Cloudflare's problem, not ours. The admin Worker can optionally double-check the signed JWT Access attaches to each request, but the heavy lifting happens before our code ever runs.

Recommended login method: Email One-Time PIN (OTP). Cloudflare Access supports several identity providers -- email OTP (Cloudflare emails a one-time code on login, no account/password needed anywhere), or SSO via Google/GitHub/Microsoft if admins already have accounts with those. For a small team, email OTP is the simplest default: it works for literally any email address on the allowlist with zero setup per-admin, requires no OAuth app registration, and nobody needs to remember a separate password. If the team already standardizes on Google Workspace/Gmail accounts, Google SSO is a reasonable upgrade later -- but OTP is the right starting point.

How a new gallery image reaches the public site

The public /gallery page stays static (fast, cheap, SEO-friendly, unchanged for visitors) rather than being converted to render on every request. The loop looks like this:

  1. Admin logs in (Cloudflare Access) and uploads an image + category + caption
  2. Admin Worker validates the file, writes it to R2, inserts a row into D1
  3. Admin Worker calls a Cloudflare Deploy Hook on the public site's project — the same mechanism a normal git push already triggers
  4. The public site's build runs; Gallery.astro's frontmatter fetches the current rows from D1 (via Cloudflare's D1 REST API, a plain fetch call usable during astro build) instead of the hardcoded array
  5. New image is live on /gallery within roughly a minute, same categorized grid/lightbox UI as today

Trade-off accepted deliberately: a short delay between upload and the image going live, in exchange for keeping the public gallery page 100% static. See the "shared D1/R2" open decision below for the alternative (a live/dynamic gallery page).

Architecture overview

One Cloudflare Worker (kriyayogamission-admin) serves two things from one deploy: the built React SPA (static assets, via the ASSETS binding) and all /api/* routes. @cloudflare/vite-plugin runs both halves under one Vite dev server locally, with HMR. The Worker owns three Cloudflare-native bindings: R2 (GALLERY_BUCKET, raw image bytes), D1 (DB, gallery metadata), and ASSETS (the React build). Cloudflare Access sits in front of the whole domain at the edge, before any request reaches this Worker's code at all.

Cross-repo contact ingest (added 2026-11-07)

Closes the "contact-form-log" gap below without re-architecting who sends the notification email. The public site's worker.js keeps its existing, unchanged Resend call -- this is purely an additive safety net alongside it. Flow per submission:

  1. Persist first, awaited: before calling Resend at all, worker.js POSTs the raw submission to this Worker's /api/public/contact-messages, creating a D1 row with email_sent=0. Deliberately awaited, not fire-and-forget -- if this were ctx.waitUntil'd instead, a Resend-side hang or an unhandled exception further down could still end the request before the durable write happened, recreating the exact gap this feature exists to close.
  2. The existing Resend call runs exactly as before -- same request shape, same error handling, same response to the visitor. This step is completely untouched.
  3. Backfill, fire-and-forget: once Resend's call resolves (success or failure), worker.js fires a ctx.waitUntil'd PATCH to /api/public/contact-messages/:id with the real outcome. Allowed to be lossy -- the row's mere existence from step 1 is the actual safety net.

Auth: a shared-secret bearer token (CONTACT_INGEST_TOKEN), same value set via wrangler secret put on both Workers -- simpler than Cloudflare Access Service Tokens, consistent with the "URL itself is the credential" simplicity already established by the deploy-hook mechanism. worker/types.ts fails closed (503, not open) if the token isn't configured on this side yet.

Backward compatibility, verified: both new runtime vars (ADMIN_CONTACT_API_URL, CONTACT_INGEST_TOKEN) are optional on the public site's Worker -- if either is unset, worker.js's new code paths are silent no-ops and the contact form behaves exactly as it did before this change (confirmed locally: ran wrangler dev for both Workers side by side, submitted with the vars unset -- identical response, no new log noise -- then again with them set and a deliberately-broken Resend key -- the visitor still saw the same error message as before, but the submission was captured in D1 with email_sent: false, exactly the scenario this feature exists for).

Email metrics (added 2026-11-07)

worker/lib/resend-client.ts pages through Resend's own GET /emails list endpoint (cursor-based, 100/page, capped at 20 pages / 2000 emails -- comfortably above this site's real volume) to compute total sent, sent today, sent this month, a 14-day daily breakdown, and a count per Resend last_event (sent/delivered/bounced/complained/...). This answers "how many emails have we actually sent / did they deliver" directly from Resend's own records, which is a different (and more authoritative) question than "how many contact messages did we receive" -- the two numbers can diverge, and that divergence is itself surfaced as attemptedButNeverReachedResend (count of contact_messages rows where email_sent=0 -- submissions that never even became a Resend email at all, e.g. during a Resend outage or bad API key). Requires its own RESEND_API_KEY_ADMINPANEL secret on this Worker -- deliberately a brand-new Resend API key, never the public site's existing sending key, named distinctly (_ADMINPANEL suffix, per explicit request) so there's zero chance of ever confusing the two or accidentally touching the production sending key. This dashboard only ever needs read access (GET /emails), never send capability.

Historical backfill (added 2026-11-07)

The contact_messages table only starts capturing submissions from the moment the public site's worker.js change went live -- anything sent earlier only exists as an email in Resend's history, invisible to the Contact Messages page. A one-time, idempotent backfill (POST /api/contact-messages/backfill-from-resend, triggered by an "Import historical messages from Resend" button on the page) recovers these:

  1. Lists every sent email via GET /emails, filters to ones whose subject exactly matches the public site's notification subject string ("New Inquiry for - Kriya Yoga Mission")
  2. Skips any whose Resend email id already exists in contact_messages.resend_message_id -- this is what makes re-running the button safe; nothing is ever duplicated
  3. For each new candidate, fetches the full HTML body via GET /emails/:id and reconstructs name/email/phone/address/message by parsing it with worker/lib/contact-html-parser.ts -- deliberately coupled to the exact template string literal in the public site's worker.js, since that's the only source of truth for what the HTML looks like
  4. Inserts recovered rows with backfilled=1, status='read' (not 'new' -- these were already seen via the original email, so defaulting to 'new' would misleadingly flood that tab with old noise), email_sent=1, and created_at set to the email's own send timestamp (a close but not exact proxy for the original submission moment)

Limitations, surfaced honestly rather than hidden: this can only recover submissions whose email matches the current notification template exactly -- if that template ever changes, older backfills still work (they were captured at the time) but the parser would need a matching update to keep working on anything sent after the change. source_ip is always null for backfilled rows (Resend never knew it), and backfilled cards show an "Imported from Resend" badge in the UI so admins know these are reconstructed, not originally captured with full fidelity. Capped at 300 new imports per run (MAX_BACKFILL_PER_RUN) to bound Resend API usage and Worker execution time per click -- safe to click the button again for a second pass if ever exceeded.

Self-diagnosing result (added 2026-11-07): the response also reports totalEmailsInResendAccount, excludedBySubject, and up to 10 nonMatchingSubjectSamples -- added after a real mismatch (Resend's own dashboard showed 9 sent emails, the admin panel only showed 6) needed investigating without direct Resend dashboard access. Rather than guessing, the admin can now see exactly how many of Resend's emails were excluded purely because their subject line didn't match, and what those subjects actually were -- e.g. test emails, a changed subject line from an older worker.js version, or genuinely unrelated sends from the same account.

Contact Messages UX: collapsed-by-default cards (added 2026-11-07)

With potentially years of backfilled history in one list, rendering every full message body at once made the page an unscannable wall of text. Each ContactMessageCard now starts collapsed -- showing only name, a truncated email, status/backfilled/unconfirmed badges, the date, and a single-line message preview -- and expands in place on click to reveal the full address, full message body, and the status/delete actions. This is local component state per card (a plain useState, not lifted to the page), so expanding one card never affects any other card or triggers a re-fetch. Applies uniformly across the All/New/Read/Replied tabs since they all render the same card component.

Contacts directory tab (added 2026-11-07)

A fifth tab, Contacts, alongside All/New/Read/Replied -- a deduplicated "who has contacted us" view: Name, Email, Phone, Address, message count, and first/last-contacted dates. Deliberately excludes message content entirely, per explicit request -- this is a contact directory for outreach/mailing-list purposes, not a message archive.

Computed entirely from contact_messages at request time (GET /api/contacts, see worker/api/contacts.ts) -- there is no separate table and no write path to keep in sync, so this view can never drift from the underlying messages. SQLite's ROW_NUMBER() OVER (PARTITION BY email ORDER BY created_at DESC) window function picks each email's single most recent row for name/phone/address (a plain MAX() would only give the max of each column independently, not "all three columns from the same latest submission"), joined against a separate aggregate for message count and first/last-contacted timestamps. If the same person has submitted more than once with different details, their most recent submission's name/phone/address wins -- the same behavior you'd want from an up-to-date mailing list. Verified locally: two submissions under the same email correctly collapsed into one directory row with the latest details and a message count of 2.

Resend daily send limit tracking (added 2026-11-07)

Resend's free tier caps outbound sends at 100/day. The existing "Sent Today" KPI on the Email Delivery card (already sourced live from Resend, see "Email metrics" above) now visually tracks this: a caption always shows X / 100 daily limit, the card's border and caption turn amber at 80% (RESEND_FREE_PLAN_DAILY_LIMIT and WARNING_THRESHOLD_RATIO in EmailMetricsCard.tsx), and red once the limit is reached. This is a hardcoded constant, not read from Resend's API -- there is no endpoint that reports an account's actual plan limit, so it needs updating by hand if the account ever moves to a paid plan with a different (or no) cap.

Recommendations for handling the limit if/when it's actually crossed (deliberately not implemented -- these are organizational/plan decisions, not something to silently automate into the codebase):

  • Upgrade the Resend plan if the 100/day cap is being hit organically from legitimate contact-form traffic -- the simplest fix, and the right one if the mission's actual inquiry volume has genuinely grown past the free tier.
  • Separate transactional traffic from the contact form, if other email types share this Resend account -- e.g. a future newsletter or donation-receipt feature should probably use its own Resend API key/domain so a spike in one doesn't starve the contact form's quota.
  • Queue instead of drop on rejection -- since every submission is already persisted to D1 BEFORE the Resend call (this is the whole point of migration 0004), a 429/limit-exceeded response from Resend never loses the inquiry itself, only delays its notification email. A small follow-up could retry queued "email_sent=0" rows the next day once the quota resets, rather than requiring a manual re-check.
  • Alert rather than silently degrade -- e.g. a scheduled Worker (Cron Trigger) that checks sentToday once daily and sends a one-off warning (via a channel other than Resend itself, to avoid a circular dependency) if it's approaching 100, so the organization isn't surprised by a reset-at-midnight gap.
  • Treat it as a soft problem, not a hard outage -- the Contact Messages page itself has zero dependency on Resend's quota (D1 persistence happens regardless), so even a fully exhausted daily quota only delays the admin's awareness by however long it takes someone to check the Contact Messages page directly instead of waiting on an email notification.

Auth & security design

Admin login: Cloudflare Access (Zero Trust) in front of the whole domain, email-allowlist policy, Email OTP identity provider -- exactly as originally decided. The Worker never sees a password or builds a session; it just trusts the Cf-Access-Authenticated-User-Email header Access attaches to authenticated requests (used for /api/me and to stamp uploaded_by).

Google API auth (GA4 + Search Console): hand-rolled token exchange in worker/lib/google-auth.ts using plain fetch + the Web Crypto API (Google's official Node client libraries don't run in the Workers runtime). Two interchangeable credential flavors are supported, auto-detected from whichever secrets are set: an OAuth refresh-token flow (preferred -- a one-time human consent grants a long-lived refresh token, no service-account key file ever exists, keeps working even under an org policy that blocks service-account key creation) or a classic service-account JWT-bearer flow as a fallback. Both GA4 and Search Console reuse the exact same credential pair, each requesting its own OAuth scope (analytics.readonly / webmasters.readonly) at token-fetch time. Access tokens are cached per-scope in a module-level map for the life of the Worker isolate (Google tokens last ~1 hour) to avoid re-authenticating on every dashboard load.

Secrets hygiene: real credentials (GA4_SERVICE_ACCOUNT_PRIVATE_KEY, GA4_OAUTH_CLIENT_SECRET, GA4_OAUTH_REFRESH_TOKEN, etc.) are set via wrangler secret put, never committed. Non-sensitive identifiers (GA4_PROPERTY_ID, GSC_SITE_URL) live as plain vars in wrangler.jsonc -- with a documented gotcha that vars (unlike secrets) get fully overwritten by whatever's committed on every deploy, so they must always be edited in the file, never by hand in the dashboard.

Deploy automation

Every create/update/delete on a gallery image fires-and-forgets (ctx.waitUntil) a POST to a Cloudflare Deploy Hook URL (worker/lib/deploy-hook.ts), the same mechanism a normal git push triggers -- so the next build of the public site's /gallery page picks up the change. This replaced an earlier, less reliable approach that pushed an empty commit via the GitHub API to force a rebuild, which was retired after hitting persistent 525 errors reaching api.github.com. Originally dev-only; extended 2026-11-06, per explicit request, to fire two hooks in parallel -- DEPLOY_HOOK_URL for the kriyayogamission-dev project's dev branch, and PROD_DEPLOY_HOOK_URL for the production kriyayogamission project's main branch -- so an admin upload now reaches both dev.kriyayogamission.org/gallery and kriyayogamission.org/gallery at the same time. This only works once ADMIN_GALLERY_API_URL is also set as a Build variable (not Runtime) on the production project -- Gallery.astro's fetch logic was already environment-agnostic, it just needed something to actually trigger a production build. Each hook is independent and a silent no-op if its URL isn't set, so one missing/misconfigured hook never blocks the other.

Login & shell

Visiting the admin domain's /welcome path shows a branded, dark-theme landing page before Cloudflare Access's own hosted Email-OTP login screen. Gallery page (default view)

  • Published / Drafts tabs, each with a live count badge
  • Search box (matches caption or alt text) and a category dropdown filter; selections reset when the active tab/category/search changes so a stale bulk-selection can't silently act on hidden photos
  • Add Photo opens a modal supporting multi-file upload with a category picker, per-file caption/alt text (with quick-fill to copy one caption/alt-text across a whole batch), and an image preview; the modal closes immediately and upload progress continues in a persistent bottom panel, with the grid refreshing photo-by-photo as each upload settles
  • Each photo card supports inline Edit (caption/alt/category/order/published) and Delete, plus a selection checkbox
  • Bulk action bar appears once 1+ photos are selected: bulk edit (shared category/published-state change) or bulk delete with a confirmation prompt

Contact Messages page (added 2026-11-07)

  • Email Delivery card at the top: sent-today / sent-this-month / all-time-sent / never-reached-Resend KPI tiles, a 14-day sparkline, and a chip row of counts by Resend's own delivery status (sent/delivered/bounced/complained/...) -- all sourced live from Resend's API, see the Technical Design section above
  • All / New / Read / Replied tabs with live count badges, same tab pattern as Gallery's Published/Drafts
  • Each submission renders as a card: name (mailto link), email, phone, address, the full message, a colored status badge, and a created-at timestamp. A status dropdown lets an admin move it through new → read → replied; a delete button removes spam/duplicates
  • An "Notification unconfirmed" badge appears on any submission whose notification email never confirmed as sent -- the one place an admin can actually see a submission the old email-only flow would have silently dropped
  • An "Import historical messages from Resend" button recovers pre-feature submissions from Resend's send history (see "Historical backfill" in the Technical Design section); safe to click more than once. Recovered cards show an "Imported from Resend" badge so admins know those specific rows are reconstructed rather than originally captured. The result summary also reports total Resend emails found, how many were excluded by subject, and sample non-matching subjects -- self-diagnosing if the imported count looks lower than expected.
  • Every message card is collapsed by default, showing just name/email/badges/date and a one-line preview; clicking a card expands it in place to show the full address, full message, and status/delete actions. Applies on all four tabs (All/New/Read/Replied).
  • A fifth Contacts tab shows a deduplicated Name/Email/Phone/Address directory (plus message count and first/last-contacted dates) with no message content -- a contact list for outreach purposes, distinct from the message log itself.
  • The Email Delivery card's "Sent Today" KPI now visually tracks Resend's 100/day free-tier cap -- a quiet caption normally, turning amber then red as the day's count approaches and reaches the limit.

GA4 page

  • A 7-day / 30-day / 90-day range toggle, its own page under the sidebar's "Analytics" section (separate from Search Console -- see below)
  • An all-time total-visitors badge and a live "active right now" realtime badge (GA4 Realtime API)
  • KPI cards (total users, new users, sessions, engagement rate, avg. session duration, conversions) each with a period-over-period delta; a users/sessions timeseries chart; donut charts for traffic channels, devices, and new-vs-returning; tables for top pages and top countries
  • Degrades gracefully to a plain "isn't connected yet" message if GA4 credentials aren't configured, instead of crashing the page

Search Console page

  • Its own page and its own 7/30/90-day range toggle, independent of the GA4 page's selection
  • KPI cards for clicks/impressions/CTR/avg. position with period-over-period deltas
  • Filter bar (added 2026-11-07, modeled on GSC's own "+ Add filter" picker): Query and Page filters each support containing / not-containing / exact match; Country and Device are plain exact-match selects. All four are forwarded server-side as GSC dimensionFilterGroups and apply to every section on the page (summary KPIs, Keyword Rankings, and the dimension breakdown tabs below) -- not just one table, matching how filters behave in real Search Console. Applied filters render as removable chips. The Country select's option list is deliberately fetched unfiltered on every range change so picking one filter doesn't make other filter options disappear. Regex filtering (GSC's 4th option) isn't supported yet.
  • Keyword Rankings report (the headline addition requested 2026-11-07): every query from the selected range/filters (up to 250, GSC's own per-request rows sorted by clicks) is classified Branded vs. Non-Branded by shared/brand-terms.ts's BRAND_TERMS list (the exact organization name, its domain, "kym", and the current guru's name -- deliberately NOT the generic term "kriya yoga" itself, since that's a topic thousands of unrelated pages compete for, not evidence of brand recognition). Two tabs, each with its own keyword-count/total-clicks/total-impressions/avg-position summary (recomputed live via shared/search-console.ts's aggregateQueryStats) and a scrollable table. Branded tab filters via a select-from-list of the known brand terms (a small, finite vocabulary suits a dropdown); Non-Branded tab filters via free-text type-to-search (an open-ended, 200+-row list has no fixed vocabulary, so a dropdown doesn't fit). Both filters run client-side over the already-fetched group -- no extra Google API call. Defaults to the Non-Branded tab open, since that's the traffic SEO work is actually trying to grow.
  • Dimension breakdown tabs (added 2026-11-07): Queries / Pages / Countries / Devices / Search Appearance -- the same five report tabs Search Console's own Performance page offers (its sixth, "Days", is intentionally skipped as a duplicate of the GA4-style timeseries chart pattern, which this page doesn't currently render for Search Console data -- a gap, not a decision, see below). Replaces the earlier single "top pages table + device donut" with the full GSC-style breakdown, including CTR and position columns the donut couldn't show.
  • Degrades gracefully to a plain "isn't connected yet" message if Search Console credentials aren't configured

Deliberately out of scope for now: a Search Console-side timeseries/"Compare" overlay chart (GA4's page has one; period-over-period deltas on the KPI cards cover the same need more cheaply); the "24 hours" range option (meaningless against data that's already ~3 days lagged, see DATA_LAG_DAYS in worker/api/search-console.ts); the Search type filter (web/image/video/news -- this is a text-heavy site with no meaningful image/video/news search presence to filter by); and regex-based filters. All are easy to add later if the need actually shows up.

YET TO DEVELOP Analytics API Expansion -- going beyond what GA4 alone can tell us

Follow-up research after a question about which other Google/Cloudflare APIs would surface more real information than the GA4 dashboard already shipped above. Nothing in this section is built yet -- it's captured here so the reasoning and recommendation aren't lost, and so a future "let's add X" request doesn't have to re-derive this from scratch.

Two myth-busters first

  • "Google Analytics Admin API" does not get more visitor data. It's a config/management API (data streams, custom dimensions, conversion events, user access, property settings) -- think "Terraform for your GA4 property," useful for automating setup/audits, not for understanding traffic better.
  • "Analytics Hub API" is a total red herring despite the name -- it's a BigQuery product for publishing/subscribing to shared datasets between organizations (e.g. buying a dataset from a vendor). It has nothing to do with website analytics and solves no problem this project has.

What would actually get more real information

GA4 → BigQuery ExportRaw, unsampled, event-level data (every event, every custom param) instead of the Data API's aggregated/sampled reports -- arbitrary SQL, custom funnels GA4's UI can't buildMediumFree (daily batch); streaming is GA4 360 only
Chrome UX Report (CrUX) APIReal-world page-speed/Core Web Vitals (LCP, INP, CLS) from actual Chrome visitors -- zero overlap with GA4LowFree

Cloudflare Web Analytics / GraphQL Analytics APIServer-side truth GA4 structurally cannot see: bot traffic, WAF/firewall-blocked requests, cache hit ratio, edge response times, traffic that never ran GA4's JS (ad-blockers, bots, crawlers)Low-MediumFree, included in every CF plan
YouTube Data/Analytics APIView counts, watch time, audience retention -- only if a YouTube channel with embedded videos existsLowFree

Ranked recommendation

  1. Cloudflare Worker/Web Analytics -- biggest bang for buck, zero new Google auth complexity, and the only source here that sees traffic GA4 structurally misses (bots, blocked requests, ad-block users).
  2. GA4 → BigQuery Export -- the single most powerful upgrade if/when the Data API's aggregated reports stop being enough (e.g. "what sequence of pages do converting visitors follow"). ~10 minutes to link in GA4 Admin → BigQuery Links; querying it from the Worker afterward is a separate, bigger project (BigQuery client, billing account) worth scoping on its own.
  3. CrUX/PageSpeed API -- cheap, fast win for "how healthy/fast is our site for real users," a single new dashboard card, API-key auth only (no OAuth/service-account plumbing).
  4. YouTube/Business Profile APIs -- only worth it if those channels actually exist and matter to the mission's outreach.
  5. GA4 Admin API -- park it; nice-to-have for automation someday, not an insight source.
  6. Analytics Hub API -- don't build this; it doesn't do what the name implies.

Suggested Solution -- follow these while building

Everything below is a final, locked-in recommendation from the discussion above. Treat this as the checklist of defaults to follow unless a specific future decision explicitly overrides one.

  • • Public site (kriyayogamission.org) stays Astro, fully static -- do not migrate to React/Next.js. Use a React "island" (@astrojs/react) only if a specific future feature genuinely needs heavy client-side interactivity.
  • • Admin panel frontend: TypeScript + React, built with Vite, as a static SPA -- no Next.js/Remix SSR. Ships as plain static files served via the admin Worker's assets binding.
  • • Admin panel backend / API routes: TypeScript on Cloudflare Workers -- same pattern as the public site's worker.js. No Python, no separate Node.js server, no Rust (nothing here is CPU-bound enough to justify it).
  • • Login / IAM: Cloudflare Access (Zero Trust) gating the admin domain, policy-based email allowlist, Email OTP as the default identity provider. No custom login page, password storage, or session code to build.
  • • Image storage: Cloudflare R2. Structured data (categories, captions, order): Cloudflare D1.
  • • Public gallery stays static: admin publishes -> writes to R2/D1 -> triggers a Cloudflare Deploy Hook -> public site rebuilds -> Gallery.astro fetches current D1 rows at build time. No live/dynamic rendering of /gallery.
  • • Repo: new, separate GitHub repo kriyayogamission-admin, with its own dev/main branch strategy mirroring the public site's.
  • • Deploy target: a new, separate Cloudflare Worker project, Git-connected, same auto-build pattern as kriyayogamission / kriyayogamission-dev.
